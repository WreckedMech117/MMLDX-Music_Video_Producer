## 2026-08-17 — Story expansion: a timed plan becomes a fully prompted one

Closed under `spec-2-2-story-expansion-into-prompted-shots.md`. Nothing in the application turned a Treatment, a Style Bible and timed Shot windows into a render-ready prompt per Shot. `Shot.prompt` defaults to `""`, no code validated it, and the plan could reach submission unprompted or still carrying the `"New shot"` placeholder the timeline writes. The Director chat could write prompts, but only positionally and only as a side effect of conversation.

- Added `POST /api/projects/{id}/director/expand`, one **whole-plan** call rather than one call per Shot. Per-Shot calls cannot see each other, and the variance FR-26 asks for — identity, wardrobe, palette and lens held fixed while action, framing and energy move — is a property of the plan, not of any one Shot. Twelve independently written prompts that each "hold the identity" read as twelve takes of one shot.
- **Results are keyed by Shot id, never by position.** This is the load-bearing decision, and it is why `ExpandedShot` exists as its own model instead of reusing `PlannedShot`, which has no id. The chat route's positional merge is survivable for `start`/`duration`, where a wrong assignment shows up as a visibly wrong window; a prompt is free text, so the same mistake after a concurrent add, delete or split reads as a plausible prompt on the wrong Shot forever and nothing downstream fails. A route test commits a Shot insertion at the front of the list while the model call is in flight; the positional mutation of the merge fails it.
- **The model's input is a purpose-built, trimmed, pure builder**, `timeline.expansion_input(project)`, and the route is a thin delegator over it. Two reasons. First, the recorded root cause of Director degradation is rich context, and the chat route's dump ships every Shot's `status`, `prompt_id`, `latest_output`, `latest_review` and `approved_output` — none of which says anything about how to write a prompt. Second, the acceptance criterion "the input verifiably includes each Shot's position within the Song" is **unfalsifiable against the route alone**: the chat dump already carries start, duration and end, so it would be satisfied by doing nothing. A named pure builder can be asserted directly, and a route test asserts the builder's output is what `expand` was handed, verbatim.
- **The song-section slot is empty, and the honest implementation of "when analysis exists" is to say so.** FR-26 asks for section boundaries when analysis exists; there is no analysis anywhere in this project — no BPM or section field on `Song`, `Project` or `Shot`, the analyse-structure button is a disabled stub, `#bpm-value` and `#sections-value` are hardcoded "Not analyzed", and `#section-track` is never populated. `timeline.song_section` is therefore one named empty branch with a docstring saying why, and the key is **omitted** from the payload rather than sent as `""` or `"unknown"`. A test asserts both halves: absent from every Shot, and no model field anywhere that a section could have come from. `song_fraction` is absent the same way when there is no Song or its duration is 0 — a fabricated 0.0 tells the model every Shot opens the song, which is worse than telling it nothing.
- **No render, ever, and no retiming.** The route never touches `comfy`, never advances a `status`, and assigns only `prompt`. Tests assert `comfy.prompts` stays empty and every window is unchanged. Window checks are **descriptive flags** on the input rather than a gate, because expansion writes prompts only and nothing new can fail; blocking on prompt quality is Story 2.3's readiness gate and is deliberately not done here.
- Three failures are **reported rather than guessed at**: an id matching no Shot is discarded and named (creating one would invent a window this route has no business choosing), a Shot the model omitted keeps its prompt and is named (a retry loop spends the Director's time on a model that already declined), and a prompt that parses as JSON is refused by the FR-15 `document_rejection` check and named. Only the JSON half of that guard is used — `""` is passed as the existing text on purpose, because the 40% ratio floor compares against a prompt that is `""` or `"New shot"`, so it is toothless where it matters and would refuse a legitimate first prompt on a Shot written by hand. A whitespace-only prompt is refused separately: this route must not be the thing that blanks a prompt.
- Extracted the unloaded-model retry into `DirectorClient._completion`. It was duplicated verbatim in `plan` and `inspect_image`, and `expand` would have been the third copy; the test exercises all three call sites, because an extraction that leaves one behind still passes a test that only drives `plan` — and the one left behind is the one that fails against a real LM Studio.
- Frontend: the disabled `#apply-shot-plan` stub, whose handler only toasted, became the expansion action `#expand-shot-prompts`. No new surface. The button says what it does not do ("Nothing is rendered"), in the one wording the toast also carries. Review then closed three holes in the first cut: awaiting the pending shot-save chain only drained saves pending *at click time*, so a drag *during* the multi-second call still queued a stale whole-list save that landed afterwards and reverted every prompt just written — silent shot saves are now refused for the duration; the result was assigned to `state.project` with no check that the Director had not switched projects mid-call, which would have drawn one project's shots and documents under another's name; and the toast diffed shots before and after, so a re-run against a model returning the same prompts said "no shot prompt changed" directly beneath a reply saying prompts were written. The toast is now read from the reply itself, which removed the need for the before-snapshot entirely.
- Added twenty tests: eleven route tests in `tests/test_api.py` (every I/O matrix row plus the verbatim hand-off, the trimmed input, the blank-prompt guard and the concurrent add), five builder tests in `tests/test_timeline.py`, two in `tests/test_director.py` for the `expand` wire shape and the retry extraction across all three call sites, and two in `tests/test_frontend_contract.py`. The existing unconfigured-director test was extended to cover `expand` as well. Every mutating route test re-reads through a **fresh `ProjectStore`**.

What review closed: expansion rewrote the prompt of a Shot that had already rendered or been approved, so an approved take and the prompt beside it would quietly disagree — Shots carrying render provenance are now skipped and reported, which also means marking a Shot `ready` takes it out of expansion's reach. A duplicate `shot_id` in one reply was applied last-write-wins and could report one Shot as both refused and written; the first answer now wins and the contradiction is named. A locked Shot the model skipped was told to "run expansion again", which would never write it. The model was given one index (by start) while the notices named another (manifest order). `song_fraction` was unclamped, so a Shot past the song's end claimed to sit at 3.5x of it. ## 2026-08-17 — Document replacement becomes opt-in per turn

Closed under `spec-2-1b-document-replacement-opt-in.md`, building directly on the entry below. Story 2.1 made an unrequested document rewrite **visible and reversible**; it never made it **consented**. Every Director turn still replaced the Treatment and the Style Bible whatever the Director had actually asked for, so "what do you think of this idea?" rewrote both documents and then honestly reported that it had. Shot application — the cheaper, more easily redone artefact — already required `apply_shots`; the documents did not.

- Added `apply_documents` to `DirectorRequest`, defaulted off and mirroring `apply_shots` in shape, default and independence. The guard loop writes nothing without it. The flag is **not** stored on `Project`, and — after the review recorded below — the control is cleared in the two places that make "per turn" true rather than merely intended: in the send handler's `finally`, so the consent a turn carried is spent by it, and at the top of `loadProject`, so consent given in one project is never inherited by the next. A client that omits the field, or sends it as `null`, is read as a decline. That was the spec's one open question and it is resolved the safe way — the cost, stated plainly, is that a Director who wants every turn applied ticks the box every turn.
- **The first cut shipped that sentence without the code to back it.** Nothing ever unchecked the box: one tick applied every later turn with no fresh consent, and the box survived a project switch, so the feature was "on until the Director notices" rather than opt-in — and this paragraph said otherwise. Recorded because the failure was not the missing line, it was claiming a guarantee whose only evidence was the request field's default. The lifecycle is now executed rather than grepped: `documentConsent` and `clearDocumentConsent` are pure functions in `api.js` over the control element, and a node test ticks, sends, clears, and reads back to prove the second turn sends `false`.
- The gate sits **after** the lock check, not before it. Both mean "do not write, and say why", but a lock is durable state the Director set and the flag is one turn: with both in force, "locked" is the sentence worth reading, and reporting a locked document as merely unrequested would relabel a protection as an oversight *and* promise that ticking a box will apply it, which it will not.
- It carries the lock notice's **silence rule** for the same reason the lock has one. `DOCUMENT_NOT_REQUESTED_NOTICE` is emitted only when the candidate would genuinely have changed something and would genuinely have been applied: an echo of the current text proposed nothing, and a candidate `document_rejection` would have refused would not have landed with consent either — so naming it as merely unrequested would invite a retry that refuses identically. A declined ordinary question therefore adds no notice block at all.
- **Nothing new is persisted.** No proposal slot, no stored declined text; the wording a declined turn proposed is gone, exactly as a declined shot list's is. The notice says so, because the alternative is a Director hunting for a recovery that does not exist. The recovery slots are untouched by a declined turn — the slot is spent only when a document is actually replaced, and spending it on a turn that wrote nothing would annihilate the one recoverable version over nothing at all.
- Frontend, inside the existing chat composer rather than the document actions row, because consent belongs to the act of sending: one unchecked checkbox, read at submit time and passed through as `apply_documents`. Never hardcoded — a fixed `true` reinstates exactly the rewrite this closes, and a fixed `false` makes the control decorative, and both leave every route test green because the server stays correct about a flag the browser never sends honestly. `documentChangeToast` now takes the consent as well as the before/after project: "no document changed" is true of a declined turn and useless, so a declined turn gets `DOCUMENT_NOT_APPLIED_TOAST`, which names the control, while a lock or a rejection keeps the vaguer sentence rather than sending the Director to tick a box that was already ticked. The consent defaults to `true` in that function on purpose — it is the safe default of the two, since defaulting to `false` would blame the flag for a lock.
- The control's name exists in one place per layer and is asserted across all three: `APPLY_DOCUMENTS_LABEL` in `app.py` (quoted by the notice), `APPLY_DOCUMENTS_LABEL` in `api.js` (quoted by the toast), and the label in `index.html`. A notice telling the Director to tick a control that no longer exists under that name is worse than no notice.
- **The toast is decided by the reply, not by the diff, whenever consent was declined.** Three ways the loudest feedback on screen misstated what happened, all found in review. A restore or a hand edit committed while the Director call was in flight moves a document without this reply having touched it, and before/after cannot tell the two apart — so a declined turn could credit the reply with a replacement consent had made impossible. And the server is deliberately *silent* in four cases the client cannot see from the project alone: nothing proposed, an echo, a candidate the guard would have refused, and a locked document. Blaming the opt-in for any of those sends the Director to tick a box and retry a turn that writes nothing either way, or to tick a box that would not apply a locked document at all. `documentProposalDeclined` keys on a phrase from the server's own notice — the `DOCUMENT_RESTORE_REFUSAL_MARKER` shape — so the toast can only blame the flag where the server actually reported a declined proposal.
- **`null` is a decline, not a 422.** An omitted flag was already handled, but an explicit `null` — what many clients serialise for "unset" — failed validation and lost the Director's message over a field whose absence is the safe default. One shared `DeclinedIfNull` annotation normalises it on both consent flags; nothing else is loosened, and a value that is neither boolean nor null is still refused.
- The unsaved-edits confirm now describes the send that is actually happening. Both sends re-render the editors from the server and so discard unsaved typing — which is why the gate fires either way — but only a consented send can *replace* a document, and warning about a rewrite that cannot happen deters a send that would write nothing.
- Added fifteen tests. Seven in `tests/test_api.py`, every one re-read through a **fresh `ProjectStore`**: a declined turn writes neither document nor slot and names what it proposed, an ordinary question that proposed nothing says nothing, an omitted *or null* flag is a decline while a non-boolean is still 422, the two flags are independent in both directions, a partly locked declined turn keeps the lock's sentence and a fully locked one emits no unrequested wording at all, and a declined turn is silent about a degraded candidate. Eight in `tests/test_frontend_contract.py`, including three executed under node rather than grepped: the consent lifecycle (tick, send, clear, read back — the only thing that proves a second turn sends `false`), absence reading as a decline, and the marker asserted to be a real substring of the server's own notice against an earlier declined line, a `system` line, and four empty shapes.
- **Thirty-seven mutations reintroduced and all thirty-seven caught** by the intended test — sixteen from the first pass, re-run against the reviewed source, and twenty-one for the review's own findings. Among the second set: consent never spent by a turn; a `clearDocumentConsent` that keeps every identifier and does not clear; consent spent only on a *successful* send; consent inherited by the next project; the null guard dropped so a missing control kills the send; `null` 422ing again, or reading as consent; the declined branch decided by the diff; the toast always blaming the opt-in, and never blaming it; the marker turned into an equality check, drifted from the server's wording, or reading the wrong message; a fully locked declined turn emitting the unrequested wording; the confirm warning of a rewrite that cannot happen; and the composer row losing its wrap.
- Nine existing route tests were updated to send `apply_documents: true` rather than relying on the old unconditional write — including the two that pin the lock notice's silence and the identical-candidate skip, which would otherwise have passed for the new reason instead of the one they were written for.
- `uv run pytest` **188 passing**, `uv run ruff check .` clean, `node --check` clean on `app.js` and `api.js`. That 188 is a shared-tree figure — Story 2.2 landed in the same tree between this change's two passes; `docs/ROADMAP.md` remains the authority for the current count. Scope of the claim: these are offline tests. **The composer checkbox, its clearing, and the declined-turn toast have not been driven in a real browser**, so only the executable contract is claimed for the UI half.

## 2026-08-17 — Reviewable document replacement, with recovery and per-document locks

Closed under `spec-2-1-reviewable-document-replacement.md`; the binding decision is AD-14 in `ARCHITECTURE-SPINE.md`. FR-15 stopped *degraded* Director output from overwriting a creative document, but a plausible-looking rewrite nobody asked for passed the guard and was permanent: `director_chat` assigned `project.treatment` and `project.style_bible` unconditionally, kept no copy of what it overwrote, and the reply never said a document had changed. `DirectorResult` requires both document fields, so a model with nothing to say still returned prose that overwrote. FR-16 promised "locked fields are never modified" without a lock for documents existing at all.

- Added four defaulted fields to `Project`: `treatment_previous`, `style_bible_previous` (single-slot recovery per AD-14) and `treatment_locked`, `style_bible_locked` (the lock FR-16 requires, mirroring `Shot.locked`). Defaulted so every manifest already on disk loads unchanged; no migration.
- **Capture on apply, never on attempt.** This is the load-bearing detail, not a style choice: writing the recovery slot before `document_rejection` ran would let a rejected candidate overwrite the only copy of the good document, turning a protective refusal into the data loss it exists to prevent. The FR-15 route test was extended rather than duplicated, and now asserts that the rejected style bible leaves both the document *and* its slot untouched while the accepted treatment captures in the same call.
- A locked document is checked **before** the guard, mirroring `if not shot.locked` in the same handler. A lock is not a rejection: nothing is assigned and nothing is captured, or the lock would spend the single recovery slot on a replacement it refused to make. The unlocked document still moves, so the rule is per-document rather than a whole-reply veto.
- The reply now says what *did* change. One constant, `DOCUMENT_CHANGE_NOTICE`, prepended to the existing notice block ahead of the "was NOT replaced" lines, because what changed is what has to be reviewed and it is the thing the reply never mentioned. `DOCUMENT_LOCK_NOTICE` states the other half.
- Added `POST /api/projects/{id}/documents/{document}/restore`. It never calls the Director — the failure it exists for is the Director returning something unwanted, and asking that same Director to undo it risks a second unwanted rewrite. It **swaps** rather than pops, so a restore is its own inverse and a mis-click costs nothing, and it refuses with 409 when nothing was kept rather than blanking the live document with `""`, which would be the exact loss AD-14 exists to stop. The wording lives in `DOCUMENT_RESTORE_NOTICE`/`DOCUMENT_RESTORE_REFUSAL` beside `SONG_REPLACEMENT_CONSEQUENCE`, and the swap is recorded as a `system` line in the thread as well as toasted — the chat is the audit trail for these documents.
- The recovery slots are **excluded from the LLM context dump**, which is correctness rather than economy. The dump is the whole project, so leaving them in echoes a second full copy of both documents into every prompt, and the recorded root cause of the original corruption was degradation under rich context (JSON in context begets JSON) — precisely the failure `document_rejection` was written to catch. The two lock booleans stay in: knowing a document is off-limits is useful direction.
- Made the UI's ordinary save path stop defeating the feature. Every text field on `ProjectDocumentsRequest` defaults to `""`, so an omitted field blanks its document; a lock defaulting to `False` the same way would silently unlock both documents on every save. The locks are therefore tri-state on the wire (`None` means "leave it alone") and the recovery slots are absent from the request model entirely, so a save can neither forge, clear, nor advance a kept version. A lock stops the Director, not the human: the route still writes the text of a locked document, because otherwise fixing a locked document would mean unlock, save, edit, lock.
- Frontend, inside the existing Treatment actions row and adding no new surface: two lock checkboxes and two restore buttons. A restore button is enabled only when a version was actually kept, so its state answers "is anything recoverable?" rather than offering something that 409s. `documentRestoreNotice` in `api.js` mirrors the server's sentence so the toast and the stored thread line are the same words, and `DOCUMENT_RESTORE_REFUSAL_MARKER` mirrors the refusal so a 409 against a control that should have been disabled refreshes the stale project instead of failing identically forever — the `SONG_REFUSAL_MARKER` shape. A lock toggle persists immediately through the ordinary document save, which also carries the textareas, so nothing typed is discarded.
- Added eleven collected tests, one per row of the spec's I/O matrix plus the parity work. **Eight of the eleven were mutation-checked** — the `Shot.locked` route test and two of the three frontend contract tests were not, and review later showed why that mattered: mutating the lock-checkbox seeding, the restore-button gating, and the refusal predicate each left the whole suite green. Those gaps were closed in the review pass recorded below. The eight checked mutations were capture-on-attempt, an unexcluded recovery field, an ignored lock, locks blanked by an ordinary save, a restore that blanks instead of refusing, a slot that keeps the *oldest* version instead of the immediate one, a missing change notice, and a restore that pops instead of swapping were each reintroduced and each caught by exactly the intended test. Eight in `tests/test_api.py`, every mutating one re-read through a **fresh `ProjectStore`** because the response body is the in-memory object the handler just built. Three in `tests/test_frontend_contract.py`: the restore wording and the label map executed on both sides and compared, the refusal marker asserted to be a real substring of the server's refusal, the client's restore URL matched against a route `create_app()` actually exposes with no body and no `JSON.stringify` to carry a message in, and the save path asserted to send both locks and neither recovery slot.
- Also covered `Shot.locked` on this path, which the spec flagged as untested: a Director result that proposes a new start, duration and prompt for a locked shot leaves all three alone, and the shot the plan did not reach is kept rather than dropped.
- Left `document_rejection` untouched. FR-15 shipped, and its four unit tests plus the route test are regression cover, not a starting point for tuning.
- Resolved FR-16's undefined locking model as **per-document, human-set locks**. A finer-grained or Director-settable lock is a different design and is not implemented; "Locked-field LLM change review" remains open in `docs/ROADMAP.md` — this ships the lock and the recovery, not a review workflow.
- `uv run pytest` **136 passing** against 125 at this change's baseline commit (`b1a2d0c`), `uv run ruff check .` clean, `node --check` clean on `app.js` and `api.js`. Scope of the claim: these are offline tests. **The restore buttons, the two lock toggles, and the restore toast have not been driven in a real browser**, so only the executable contract is claimed for the UI half.

## 2026-08-17 — Song replacement safety, and a missing removal path

Closed under `_bmad-output/implementation-artifacts/spec-1-3c-song-replacement-safety.md`. Every path that changed a project's Song overwrote it unconditionally and silently, and there was no way to remove a Song at all except hand-crafting a full-project `PUT`. The epic's "no Shot data is deleted" guarantee held by accident rather than by design or test.

- Added one guard, `_require_song_replacement_confirmation(project, confirmed)` in `app.py`, raising 409 with a single shared message, `SONG_REPLACEMENT_CONSEQUENCE`, that names both dependencies: Shot windows are absolute seconds against the current song, and Assembly synchronization derives from it. It also says what is *not* at risk — no shot data is deleted, no shot window is moved — because a Director who fears losing work avoids the operation instead of understanding it. One rule, three call sites, no duplicated wording.
- The gate only fires when the project has **both** a Song and Shots. A first import, and any Shot-less project, stays frictionless; there is nothing whose timing a change can invalidate yet. Confirmation is a request-level flag (`confirm_song_replacement`, a form field on the import route and a request field on both generate routes), not stored state — the server states the consequence and refuses without acknowledgement, which is the `document_rejection` notice pattern combined with the `updated_at` 409's "refusal carries the reason" shape.
- Placement of the guard is load-bearing, not incidental. In `upload_song` it runs before `_copy_upload`, because songs are written under their own filename with no index prefix (unlike assets): a guard after the copy would have overwritten the audio it was refusing to replace. In `generate_music` and `generate_songplanner` it runs before `comfy.submit`, so a refusal costs no GPU time.
- Added `DELETE /api/projects/{project_id}/song` behind the same gate — the removal path that did not exist. It nulls `project.song`, leaves every Shot untouched, and **leaves the audio file on disk**: removal detaches, it does not destroy media, so a mistaken removal is undone by re-importing the same file. It 404s when there is no song to remove, whether or not the flag is set.
- The browser states the same consequence before sending, matching the existing `window.confirm` precedent for destructive and expensive acts. The wording lives in one exported constant, `SONG_CHANGE_CONSEQUENCE` in `api.js`, and the rule lives in one pure exported function, `songChangeNeedsConfirmation(project)`, mirroring the server's condition. `app.js` has a single `confirmSongChange(question)` helper used by the import, generate and remove handlers. It returns `proceed` and `confirmed` separately on purpose: only a real acknowledgement is sent as `confirm_song_replacement`, never a blanket `true`, or a stale local project (shots added elsewhere since it loaded) could defeat the server's gate without anyone reading the consequence.
- Added a "Remove song" control to the Song panel's waveform actions, disabled while the project has no song, and the generate path now asks the song question separately from the existing SongPlanner GPU-cost confirm — replacement happens at submit time, GPU cost is a different question, and no new render confirmation was introduced.
- Added nine collected tests. Five in `tests/test_api.py` covering the whole I/O matrix: all three unconfirmed replacement paths 409 together (with the uploaded filename deliberately colliding with the existing song's, so the pre-copy placement is what the test proves), confirmed replacement through all three routes, first import and Shot-less replacement/removal needing no flag, unconfirmed then confirmed removal, and removal with no song 404ing. Every mutating case re-reads through a **fresh `ProjectStore`** and compares `shot.model_dump(mode="json")` field-for-field; the refusal case also asserts the audio bytes are unchanged, and the removal case asserts the file still exists. Four in `tests/test_frontend_contract.py`: the consequence constant names both dependencies on both sides, the JS gate's truth table, a parity test that **executes** the Python and JavaScript gates over the same four project states and asserts they agree, and a source-level test that all three handlers call `confirmSongChange` *before* they send and pass the acknowledgement through rather than hardcoding it.
- **Initially not gated, then closed the same day.** The generic `PUT /api/projects/{id}` was left out on the grounds that it is the normal save path and gating it would break ordinary saves. Review demonstrated against the live app that it removed a Song with no acknowledgement (`PUT song=None` → 200, Song null, one Shot intact), leaving the epic's guarantee one HTTP call short of true. It is now gated in the narrow form that preserves ordinary saves: the guard applies only when the incoming Song differs from the stored one **and** the project has Shots, so an unchanged Song round-trips untouched and adding a first Song is not a replacement. Song replacement is therefore gated on all five routes that can change or remove a Song: song upload, direct Music 3, SongPlanner, `DELETE /song`, and the full-project `PUT`.
- **Still out of scope, and a different concern:** that same `PUT` can wipe **Shots** while carrying an unchanged Song. Shot-data protection through the generic save is not Song-replacement safety and is not addressed here.
- An in-flight music job is now matched to its Song by `prompt_id` before its output is reconciled, so removing or replacing a Song mid-render can neither attach a completed render to the wrong Song nor silently drop it — the output stays recoverable on the job.
- Stored song filenames now carry an index prefix, so a same-named re-import no longer destroys the previous audio.
- `uv run pytest` 117 passing, `uv run ruff check .` clean, `node --check` clean on `app.js` and `api.js`. That 117 is a shared-tree figure, not this change's own arithmetic — concurrent work was landing in the same tree; `docs/ROADMAP.md` remains the authority for the current count. Scope of the claim: these are offline tests. **The "Remove song" control and the three confirm dialogs have not been driven in a real browser**, so only the executable contract is claimed for the UI half.

## 2026-08-17 — LTX 2.5 boundary: crop instead of stretch

The Director ruled on the aspect tradeoff the boundary repair below surfaced: geometry is preserved, and trimming a few pixels is the acceptable price. The previous entry's stretch measurements stand as the record of what that run did.

## 2026-08-17 — FR-12 import duration regression guard, and the frontend defect it found

Closed under `_bmad-output/implementation-artifacts/spec-1-3b-import-duration-regression-guard.md`. FR-12 was listed as verified, but the verification only covered the server. Writing the missing frontend guard turned up a real defect.

- Found the defect: the browser defeated the server's own ffprobe fallback. The `#song-file` change handler toasted on a failed decode but never cleared `state.audioBuffer`, and the import handler sent `state.audioBuffer?.duration || 0`. So importing an undecodable file into a project that already had a decodable song sent the **previous song's** duration; `app.py`'s `resolved_duration = duration if duration > 0 else _media_duration(target)` saw a non-zero value, ffprobe never ran, and a wrong length was persisted. Song duration is the timing spine every Shot window, playback sync, and Assembly derives from, so a wrong value is worse than a missing one.
- Fixed it in two places. The decode-failure path now nulls `state.audioBuffer`, re-renders, and resets the displayed duration to `—`, so nothing survives a failure that could be mistaken for a measurement of the new file. The sent value now comes from a pure exported `songImportDuration({ decoded })` in `api.js`, which returns 0 for a missing buffer and for any non-finite or non-positive duration, and ignores every other piece of state handed to it.
- Also corrected a display bug in the same handler: the success path set `#duration-value` and *then* called `renderSong()`, which immediately overwrote it with the previously loaded project song's duration. The two statements are now ordered so the newly chosen file's length is what stays on screen.
- Added four collected tests, each mutation-checked by reintroducing the defect and confirming the test fails. Two in `tests/test_frontend_contract.py`: the pure decision executed under the node harness (a decodable buffer sends its length; a failed decode sends 0; a failed decode **with a prior buffer present** still sends 0, plus the NaN/Infinity/negative/zero shapes), and a source-level companion pinning that the handlers drop the buffer and delegate rather than reading the duration raw. Two in `tests/test_api.py`: an upload with `duration=0` into a project that already holds a 187.5 s song, re-read through a **fresh `ProjectStore`** over the same data root to prove the probed value reached the manifest and replaced the old one — the previous route test only inspected the response body, which is the in-memory object the handler had just built — and an ffprobe-unavailable case that patches `subprocess.run` to raise `FileNotFoundError` for `ffprobe` only, asserting the import still succeeds and stores 0 rather than a fabricated number.

The one saved project on disk with an imported song stores 154.5984375 s against `ffprobe`'s 154.644898 s for the same MP3 — a 46 ms decoder-granularity difference from a correct browser decode of *its own* file, not an inherited length.
