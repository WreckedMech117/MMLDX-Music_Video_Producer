It blames the opt-in only where the server actually reported a declined proposal, keyed on a phrase from the server's own notice — so the four cases the server is silent about (nothing proposed, an echo, a guard-refusable candidate, a locked document) get the neutral sentence instead of an instruction to retry a turn that would write nothing.
  - **A declined proposal is not stored.** No proposal slot, no new persisted field; the text a declined turn proposed is gone, exactly as a declined shot list's is today. The reply names *which* documents were proposed and says the text is not kept, so the Director is not led to believe it can be recovered.
  - **Locks still take precedence, and keep their own sentence.** A locked document is never written with the flag on, and with the flag off it is still reported as locked rather than merely unrequested — unticking the box must not relabel a protection the Director set as an oversight.
  - **Consent without noise.** The proposed-but-not-applied statement is emitted only when the candidate would genuinely have changed something *and* would genuinely have been applied. An echo of the current text proposed nothing, and a candidate `document_rejection` would have refused would not have landed with consent either — naming it would invite a retry that refuses identically. This is the same silence rule `DOCUMENT_LOCK_NOTICE` already carries.
  - The two flags are **independent**: `apply_shots` merges shots while documents stay untouched, and vice versa. A route test asserts both directions.
  - **Not driven in a real browser.** The composer checkbox, its clearing on send and on project load, and the declined-turn toast have offline contract tests only; only the executable contract is claimed for the UI half.

- Shot Plan readiness gate (FR-26): **implemented and regression-guarded offline on 2026-08-17.** An empty-prompt Shot reached ComfyUI and burned a full GPU pass returning noise. `generate_h3` checked only `status == "ready"` and never looked at the prompt, `compile_timeline` serialised `"prompt": ""` in silence, and nothing anywhere computed whether a plan was fit to submit or noticed that two Shots carried the same prompt. `src/music_video_producer/batch.py` now owns `readiness_report(project)` — AD-5's module, and the single implementation Epic 4's batch submission and pre-flight will call. This change measured **235 passing** when it landed, against 210 before it. `ruff check .` clean, `node --check` clean on both modules. Scope of the claim, stated exactly:
  - **Emptiness blocks; sameness warns.** Empty or whitespace-only prompts are refused and named; two prompts identical after lowercase and whitespace collapse, or sharing more than 90% of their tokens (Jaccard, so a short prompt contained in a long one is not scored as a perfect duplicate), are reported and the plan stays submittable. Sameness will never block: a repeated beat can be a deliberate choice, and a gate that refuses one is a gate that gets worked around.
  - **The guard reads `shot.prompt`, at the route, before the payload.** The reference branch builds `f"Reference map: {tags}. {shot.prompt}"`, so an empty prompt arrives downstream as a populated sentence and every truthiness check past that line passes.   - **The batch guard is currently unreachable in the shipped interface.** `#queue-ready` is enabled only by a count of Shots with `status == "ready"`, and nothing in the shipped frontend ever writes that status — new Shots and duplicates are `draft`. So the button the guard protects cannot be enabled without a hand-rolled client. The gate on the route is what actually protects a submission today; the batch check is groundwork for Epic 4's batch submission.
  - **One refusal wording per layer.** `batch.READINESS_REFUSAL` and `api.js`'s `READINESS_REFUSAL` are asserted identical under node, and a contract test enumerates every `comfy.submit` call site in `app.py`, pins the set, and asserts each Shot-sourced one guards before it submits and before the reference interpolation.
